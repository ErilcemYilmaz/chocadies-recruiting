# Uebergabe: 4.4.1 Containerisierung und CI/CD

Datum: 2026-09-25 · Commits: noch keine (wartet auf Freigabe)

## Umgesetzt

- **`server/Dockerfile`**: Multi-Stage auf `node:22-alpine`. Die Build-Stufe
  kompiliert TypeScript mit allen Abhaengigkeiten. Die Laufzeit-Stufe
  enthaelt nur `dist/` und die Produktivabhaengigkeiten (`npm ci --omit=dev`).
  Sie laeuft als Benutzer `node` (nicht root) und hat einen `HEALTHCHECK`
  auf `/health` (mit Node selbst, kein curl im Image). `CMD` in Exec-Form,
  damit Node als PID 1 `SIGTERM` direkt erhaelt. Dazu `server/.dockerignore`
  (u.a. `.env`, `node_modules`, Tests).
- **`web/Dockerfile`**: Build mit Vite auf `node:22-alpine`, Auslieferung mit
  `nginx:alpine`. `web/nginx.conf.template`:
  - `/v1/` wird an `${API_UPSTREAM}` weitergeleitet (gleicher Ursprung wie
    beim Vite-Proxy, kein CORS).
  - `/health` prueft die Kette nginx → Server-App.
  - SPA-Fallback auf `index.html`.
  - Caching: `/assets/` ein Jahr unveraenderlich, `index.html` `no-cache`.
  - Sicherheits-Header: Content-Security-Policy nur eigene Ressourcen,
    `X-Frame-Options DENY`, `nosniff`, Referrer-Policy.
  - `web/.dockerignore` schliesst `.env.local` aus.
- **`docker-compose.yml`** im Root: Dienste `server` (Port 3001 nach aussen,
  Zugangsdaten aus `server/.env`) und `web` (Port 8080). `web` startet erst,
  wenn der Healthcheck der Server-App gruen ist. Die Demo-Anmeldung der SPA
  kommt optional als Build-Argument aus `web/.env.local`
  (`docker compose --env-file web/.env.local up --build`). Im Repository
  stehen keine Zugangsdaten.
- **`.github/workflows/ci.yml`** bei jedem Push und Pull Request:
  - Job `server`: `npm ci`, Build, Tests, Newman, Audit.
  - Job `web`: `npm ci`, Build, Tests, Audit.
  - Job `api`: Redocly CLI 2.54.3, Version fixiert.
  - Job `container`: baut beide Images, startet sie mit einer
    Wegwerf-MongoDB und prueft `/health`, SPA, SPA-Fallback, 401 ohne Token,
    CSP-Header und dass der Server nicht als root laeuft.
  - Job `images`: nur Push auf `main` und nur wenn alles gruen ist. Pusht nach
    GHCR mit Commit-SHA und `latest`, Build-Cache ueber GitHub Actions.
  - npm-Cache ueber `actions/setup-node`, Minimalrechte (`contents: read`,
    `packages: write` nur fuer `images`), aeltere Laeufe desselben Branches
    werden abgebrochen.
- **`.github/workflows/deploy.yml`** (CD) mit
  `.github/workflows/_deploy-umgebung.yml`:
  - Nach gruenem CI auf `main` geht es automatisch nach Staging, danach nach
    Produktion. Produktion braucht eine manuelle Freigabe ueber das GitHub
    Environment `production`.
  - Anmeldung bei Azure per OIDC (`azure/login`), ohne gespeichertes Passwort.
  - `az containerapp secret set` fuer `MONGODB_URI`/`JWT_SECRET`,
    `az containerapp update` fuer beide Apps mit dem SHA-Tag, danach ein
    Rauchtest ueber die oeffentliche Adresse.
  - Rollback per "Run workflow" mit frueherem Tag.
  - **Solange die Azure-Secrets fehlen, ist noch keine Azure-Umgebung
    angebunden.** Der Job `vorbereitung` erkennt das, Staging und Produktion
    werden sauber uebersprungen, mit Hinweis in der Zusammenfassung. Das ist
    auch im Kopfkommentar von `deploy.yml` festgehalten.
- **`docs/deployment.md`**: lokal starten, Pipeline-Ablauf, noetige Secrets und
  Variablen, einmalige Einrichtung (Azure, GHCR-Zugriff, OIDC, Environments,
  Atlas), Rollback.
- **Server-App, zwei Korrekturen fuer den Container-Betrieb:**
  - **Fehler behoben:** `npm start` rief `dist/index.js` auf, der Build
    erzeugt wegen `rootDir: "."` aber `dist/src/index.js`. Der Server liess
    sich aus dem Build also nicht starten. Das wurde bisher nicht bemerkt,
    weil lokal `npm run dev` (tsx) verwendet wurde. Korrigiert und
    nachgewiesen: gebauter Server startet, `/health` = ok.
  - **Sauberes Herunterfahren:** `server/src/index.ts` reagiert auf
    `SIGTERM`/`SIGINT` und schliesst HTTP-Server und DB-Verbindung, statt
    nach dem Timeout der Plattform hart beendet zu werden.

## Bezug zur Aufgabenstellung

4.4 Aufgabe 1 (Planung und Design des Deployments): begruendete Wahl der
Infrastruktur und der DevOps-Tools, CI/CD mit automatisiertem Build, Test und
Deployment. Bewertet werden Qualitaet und Detaillierung des Plans, die mit
Quellen belegte Tool-Wahl sowie Nachvollziehbarkeit und Effizienz des
CI/CD-Prozesses. Die Pipeline liefert dafuer den konkreten, lauffaehigen
Nachweis.

## Entscheidungen und Alternativen

| Entscheidung | Verworfene Alternative | Begruendung (Stichworte) | Passende Quelle aus APDE_Entscheidungen_und_Setup.md |
|---|---|---|---|
| Azure Container Apps, Region Switzerland North | Vercel/Render (PaaS) | Datenhaltung und Betrieb in der Schweiz (Personendaten von Bewerbenden, DSG); Vercel/Render ohne Schweizer Region; Container bleiben portabel | DSG SR 235.1 (Art. 16 Bekanntgabe ins Ausland); BACS (2022) |
| Azure Container Apps (verwaltete Container) | eigener Server (VM) | kein Betriebssystem-Patching, automatische Skalierung und HTTPS, passt zu acht Informatikstellen ohne Administrator | Beyer et al. (2016), SRE-Buch (Toil reduzieren) |
| Azure Container Apps | Kubernetes (AKS) | gleiche Container-Grundlage, aber ohne Cluster-Betrieb; Kubernetes-Know-how fehlt im Team; Wechsel spaeter moeglich | Beyer et al. (2016); Chen (2018) |
| Container-Images (Docker), Multi-Stage | Quellen direkt auf dem Server bauen | identisches Artefakt in Test, Staging und Produktion; kleines Laufzeit-Image ohne Build-Werkzeuge | Chen (2018), Continuous Delivery; Beyer et al. (2016), Kap. 8 Release Engineering |
| GitHub Container Registry | Docker Hub, Azure Container Registry | im selben Werkzeug wie Code und Pipeline, Zugriff ueber `GITHUB_TOKEN`, keine zusaetzlichen Kosten | – (Projektentscheidung) |
| GitHub Actions | Jenkins, GitLab CI, Azure DevOps | bereits fixiert (Teil B); kein eigener Build-Server, Konfiguration versioniert im Repo | DORA (2024) |
| Tag = Commit-SHA, Ausrollen nie ueber `latest` | nur `latest` | jede Umgebung eindeutig einem Commit zuordenbar, Rollback = frueheres Tag | Beyer et al. (2016), Kap. 8 (reproduzierbare Releases) |
| Staging automatisch, Produktion mit manueller Freigabe | direkt nach Produktion | Kontrolle vor Produktion bei Personendaten; trotzdem kurze Durchlaufzeit | DORA (2024), Change Failure Rate / Lead Time |
| OIDC-Anmeldung bei Azure | Service-Principal mit Client-Secret | kein langlebiges Geheimnis in GitHub, kurzlebige Tokens | OWASP API Security Top 10 (API8 Security Misconfiguration) |
| Rauchtest der Container in der CI mit Wegwerf-MongoDB | Images ungetestet pushen | Fehler wie der falsche Startpfad fallen vor dem Push auf | DORA (2024) |
| `npm audit` nur Produktivabhaengigkeiten ab high | alle Abhaengigkeiten ab low | bricht nur bei relevanten Luecken im ausgelieferten Code, keine Fehlalarme aus Test-Werkzeugen | OWASP API Security Top 10 |
| nginx liefert SPA und leitet `/v1` weiter | CORS in der Server-App oeffnen | gleicher Ursprung, Server-App bleibt ohne CORS-Freigabe; eine oeffentliche Adresse | OWASP API Security Top 10 (API8) |
| Server-App nur mit internem Ingress | Server-App oeffentlich | kleinere Angriffsflaeche; einzig die SPA ist aus dem Internet erreichbar | BACS (2022) |

Hinweis: Die Datenbank MongoDB Atlas liegt in Frankfurt (EU, Kapitel 4.2).
Die Schweiz anerkennt die EU als Staat mit angemessenem Datenschutz, das ist
fuer die Begruendung im Text relevant.

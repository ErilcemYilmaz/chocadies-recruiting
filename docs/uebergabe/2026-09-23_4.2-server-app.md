# Uebergabe: 4.2 Server-App (Web-API Bewerbung)

Datum: 2026-09-23 · Code entstanden 2026-08-18 bis 2026-08-24 · Commits:

## Umgesetzt

- **Grundgeruest:** Node.js 22, TypeScript, Express. `server/src/app.ts` baut
  die App (ohne `listen`, damit testbar), `server/src/index.ts` verbindet die
  Datenbank und startet den Server unter `/v1`. Zusaetzlich `GET /health`.
- **Datenhaltung:** MongoDB Atlas M0 (Frankfurt), Mongoose-Schema
  `server/src/models/Bewerbung.model.ts` mit Textindex (nachname, vorname,
  stelle) und Indizes auf status/standort sowie vermittlerId.
- **Data-Access-Layer:** `server/src/repositories/bewerbung.repository.ts`
  kapselt saemtlichen Mongoose-Zugriff (anlegen, findenNachId, suchen mit
  Paging/Filter/Volltext, aendern, loeschen, Duplikatpruefung fuer 409).
  Ungueltige ObjectIds fuehren zu "nicht gefunden" statt zu einem Absturz.
- **Statusverlauf:** Jede Bewerbung speichert intern `statusverlauf`
  (Status, Zeitpunkt, aendernde Person aus dem Token). Erster Eintrag beim
  Anlegen, weitere bei jedem Statuswechsel per PUT. Wird nie an Clients
  ausgeliefert. Setzt die Zusage aus der Spezifikation um, Statuswechsel
  fuer die Auskunftspflicht nach DSG/DSGVO zu protokollieren.
- **REST-Controller:** `server/src/controllers/bewerbung.controller.ts`, die
  fuenf Operationen aus `api/openapi.yaml`:

  | Methode | Pfad | Erfolg | Fehlerfaelle |
  |---|---|---|---|
  | GET | `/v1/bewerbungen` | 200 (Trefferliste mit Paging) | 400, 401 |
  | POST | `/v1/bewerbungen` | 201 + Location-Header | 400, 401, 409 |
  | GET | `/v1/bewerbungen/{id}` | 200 | 400, 401, 404 |
  | PUT | `/v1/bewerbungen/{id}` | 200 (inkl. Statuswechsel) | 400, 401, 403, 404 |
  | DELETE | `/v1/bewerbungen/{id}` | 204 | 401, 403, 404 |

- **Authentisierung/Autorisierung:** `server/src/middleware/auth.ts`,
  JWT-Bearer-Token (HS256, Secret aus `JWT_SECRET`). Zwei Rollen (`scope`):
  - `intern`: HR-Sachbearbeitende, voller Zugriff inkl. Loeschen.
  - `personalvermittlung`: externe Personalvermittlungsfirmen mit `firmaId`.
    Sehen und aendern nur eigene Bewerbungen, duerfen weder den Status
    aendern noch loeschen (403).
  Die Token-Ausstellung (Login) ist nicht Teil dieser API.
  `server/scripts/generateTestToken.ts` erzeugt Test-Tokens.
- **Eingabevalidierung:** `server/src/schemas/bewerbung.schema.ts` (Zod) und
  `server/src/middleware/validate.ts`. Spiegelt die Constraints der
  OpenAPI-Spezifikation, lehnt unbekannte Felder ab
  (`unevaluatedProperties: false`). Fuer PUT gibt es das eigene Schema
  `BewerbungAenderung` (wie `BewerbungEingabe`, zusaetzlich `status`).
- **Fehlerbehandlung:** `server/src/errors/ApiError.ts` und
  `server/src/middleware/errorHandler.ts`: einheitliches Fehlerformat
  `{ code, meldung, details? }` gemaess Schema `Fehler` in der Spezifikation.
  Unerwartete Fehler geben keine internen Details an den Client weiter.

## Bezug zur Aufgabenstellung

- 4.2: Server-App mit Web-API fuer das Datenobjekt Bewerbung, NoSQL-Datenbank.
- 4.2.2: eigener Data-Access-Layer (Repository-Muster, Interface IPersistenz
  im Komponentendiagramm).
- 4.2.4: toolbasierte API-Tests (Postman/Newman) plus Unit-Tests (Vitest).
- Sicherheit: Zugriffsschutz nach Rolle, Validierung, keine Secrets im Repo
  (Bezug OWASP API Security Top 10, DSG/DSGVO wegen Personendaten).

## Entscheidungen und Alternativen

| Entscheidung | Verworfene Alternative | Begruendung (Stichworte) | Passende Quelle aus APDE_Entscheidungen_und_Setup.md |
|---|---|---|---|
| Schichtung Route -> Middleware -> Controller -> Repository | Mongoose direkt im Controller | Austauschbare Persistenz, testbar ohne DB, Vorgabe 4.2.2 | OMG UML 2.5.1 (Komponenten, Interfaces) |
| Zwei Validierungen: Zod (HTTP) und Mongoose (Persistenz) | nur Mongoose-Validierung | Fehler frueh mit 400 und Feldangabe, Schichten sauber getrennt | OpenAPI Specification v3.1.1 |
| JWT-Bearer mit Rollen `intern`/`personalvermittlung` | API-Keys, Session-Cookies | zustandslos (REST), passt zu externen Vermittlerfirmen | Fielding (2000), Kap. 5 (Stateless); OWASP API Top 10 (API1, API5) |
| Fremde Bewerbung liefert 404 statt 403 | 403 Forbidden | verraet nicht, dass die Bewerbung existiert | OWASP API Top 10 (API1 Broken Object Level Authorization) |
| `vermittlerId` und `quelle` serverseitig aus dem Token | Werte aus dem Request uebernehmen | Vermittler kann sich nicht als andere Firma ausgeben | OWASP API Top 10 (API3 Broken Object Property Level Authorization) |
| `vermittlerId` wird nie ausgeliefert | ganzes Dokument zurueckgeben | nur Felder aus der Spezifikation, Datenminimierung | DSG SR 235.1; OWASP API3 |
| Status per PUT nur fuer `intern`, sonst 403 | eigener Endpunkt `PATCH /bewerbungen/{id}/status` | bleibt bei den fuenf Operationen der Spezifikation; Bearbeitungsstand fuehrt nur die Personalabteilung | OWASP API Top 10 (API5 Broken Function Level Authorization) |
| Statusverlauf eingebettet im Dokument | separate Collection fuer Audit-Log | ein Datenobjekt wie gefordert, Verlauf gehoert fachlich zur Bewerbung (Aggregat) | MongoDB Data Modeling Introduction; DSG Art. 25 (Auskunftsrecht), DSGVO Art. 15 |
| Duplikat = offene Bewerbung gleiche E-Mail + Stelle -> 409 | keine Pruefung / eindeutiger Index | abgelehnte Personen duerfen sich neu bewerben | OpenAPI-Spezifikation des Projekts |
| Tests mit gemocktem Repository | Tests gegen echte Atlas-DB | schnell, reproduzierbar, CI-tauglich ohne Zugangsdaten | Beyer et al. (2016), Kap. 8 Release Engineering |

## Nachweise

Ausgefuehrt am 2026-09-23 lokal unter Windows 11, Node 22:

| Befehl (im Ordner `server`) | Ergebnis |
|---|---|
| `npm test` (Vitest + Supertest, `tests/api.test.ts`) | 20/20 Tests bestanden |
| `npm run test:newman` (Postman-Collection per Newman gegen die App, Repository gemockt) | bestanden, 12 Requests ohne Fehler |
| `npm run build` (TypeScript) | fehlerfrei |
| Newman gegen laufenden Server mit **echter MongoDB Atlas** (M0, Frankfurt) | 12/12 Requests, 20/20 Assertions, Ø Antwortzeit 42 ms |
| Statusverlauf direkt in Atlas geprueft (anlegen, Status auf `in_pruefung`, Dokument gelesen, geloescht) | 2 Eintraege (`eingegangen`, `in_pruefung`) mit Zeitpunkt und `geaendertVon` |

Die 20 Unit-Tests decken ab: 401 ohne bzw. mit ungueltigem Token; Suche im
OpenAPI-Format, erzwungener Firmenfilter fuer Vermittler, 400 bei falschen
Query-Parametern; Anlegen 201, 400 bei unbekannten oder fehlenden Feldern,
409 bei Duplikat, serverseitiges Setzen von quelle/vermittlerId; Lesen 404,
400 bei ungueltiger ID, 404 fuer fremde Vermittlerfirma; Aendern mit
Statuswechsel und Protokolleintrag, kein Eintrag ohne Statuswechsel, 403
fuer Statuswechsel durch Vermittler, 400 bei unbekanntem Status; Loeschen
204 (intern) und 403 (Vermittler).

Die Postman-Collection `tests/chocadies-recruiting.postman_collection.json`
enthaelt 12 Requests (01 bis 12), die einen vollstaendigen Lebenszyklus
durchspielen: anlegen, Duplikat, Validierungsfehler, lesen, suchen, aendern,
Zugriffsschutz, loeschen, erneut lesen.
